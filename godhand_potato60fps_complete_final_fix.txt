1. CULPRIT #1 (OPPO F31 Pro 25–27 EE FPS Dip & Micro-Stutter):
   Core 5 (Cortex-A78 big_cores[2]) 3-Way Thread Collision in `thread_affinity.cpp`
   --------------------------------------------------------------------------------
   In `godhand_detail_logcat_oppof31pro.txt` (Section 2, PID 24635):
     - EEThread     (TID 24680): 65.5% CPU
     - IOPThread    (TID 24681): 51.7% CPU (1:07.76 CPU time — 2nd heaviest thread!)
     - VUThread     (TID 24687): 34.4% CPU (down from 90%+ thanks to the VU1 fix!)
     - GSThread     (TID 24668): 24.1% CPU
     - RenderThread (TID 24653): 13.7% CPU
     - MainThread   (TID 24635): 13.7% CPU
     - GIFThread    (TID 24686):  6.8% CPU

   Why did the Dimensity 7300 stutter when `VUThread` was only 34.4% CPU?
   Look at `thread_affinity.cpp` in the `else if (big_cores.size() >= 4)` branch
   (taken on Dimensity 7300 because `top_tier == 2`, Cortex-A78 `Part=0xd41`):
     - `EE_MAIN`     -> `big_cores[0]` (Core 7 @ 2.50 GHz)
     - `VU1_WORKER`  -> `big_cores[1]` (Core 6 @ 2.50 GHz)
     - `GS_RENDERER` -> `big_cores[2]` (Core 5 @ 2.50 GHz)
     - `IOP_WORKER`  -> `big_cores[2]` (Core 5 @ 2.50 GHz)  <-- COLLISION!
     - `GIF_WORKER`  -> `big_cores[2]` (Core 5 @ 2.50 GHz)  <-- COLLISION!

   We had moved `IOP_WORKER` to `little_cores` and `GIF_WORKER` to `big_cores[3]`
   ONLY in the `top_tier <= 1` (Redmi 10A) branch, leaving `GSThread` (24.1%),
   `IOPThread` (51.7%), and `GIFThread` (6.8%) ALL pinned to the EXACT SAME single
   Cortex-A78 core (`Core 5`, `24.1% + 51.7% + 6.8% = 82.6%` CPU contention) on
   the Dimensity 7300 while `big_cores[3]` (`Core 4` @ 2.50 GHz Cortex-A78) sat
   100% IDLE! Every time `IOPThread` woke up on `Core 5`, it preempted `GSThread`
   mid-frame during peak 97.3 MB/s GIF combat!

2. CULPRIT #2 (OPPO F31 Pro Double-VBlank Pacing Jitter to 25–27 EE FPS):
   `PS2X_MTVU_VBLANK_WAIT=0` Accidentally Disabled the 2ms Late-VBlank Re-Anchor!
   --------------------------------------------------------------------------------
   Look at `EeScheduler::processDueDeadlines()` (`EeScheduler.cpp` line 2714):
     const auto catchUp = ps2x::asyncvif::vblankWaitEnabled() &&
                          ps2x::asyncvif::active(m_runtime.memory()) &&
                          !ps2xIpuActiveRecently()
         ? std::chrono::milliseconds(2)
         : (kMaxVBlankCatchUpFields * vblankPeriod()); // 33.33 ms (2 fields!)

   When we set `PS2X_MTVU_VBLANK_WAIT=0` in `main.cpp` so `hostCatchUp()` would
   not block `EEThread`, `ps2x::asyncvif::vblankWaitEnabled()` returned `false`.
   That accidentally switched `processDueDeadlines()` from the `2 ms` late-VBlank
   re-anchor back to `kMaxVBlankCatchUpFields * vblankPeriod()` (`33.33 ms`)!
   As documented right above line 2714 in `EeScheduler.cpp`:
     "Catching up 2 fields after a late frame fired the next vblank right after
      this one; a frame that needs ~18 ms of rendering then got 2 vblanks and the
      next got none, so every image stayed 2 refreshes on screen and the next was
      skipped."
   Fixing line 2714 to ALWAYS use the `2 ms` re-anchor whenever `asyncvif::active`
   is true (without checking `vblankWaitEnabled()`) immediately restores locked
   58–60 Main FPS / 29–30 Game EE FPS with zero double-VBlank stutters on OPPO!

3. CULPRIT #3 (Redmi 10A 10–15 FPS Cap & 4-Frame Geometry Burst Stall):
   `frameskip=4` Active in `godhand_detail_logcat_redmi10a.txt` Line 179!
   --------------------------------------------------------------------------------
   Look at `godhand_detail_logcat_redmi10a.txt` line 179:
     `I GodHandRecomp: bootAndroidRuntime: initializing EE runtime (frameskip=4)...`
     `I GodHandNative: EnsureOpen: calling g_api->open (1600x720, scale=1.0)`

   On the Redmi 10A, `frameskip=4` ("Skip 3 Frames") was saved in app preferences!
   Look at what `skipMode == 4` does in `gs_pcsx2_backend.cpp` (line 729) and
   `Bridge.cpp` (line 329):
     - It sets `shouldSkip = true` for 3 out of every 4 VSyncs (capping Present
       FPS to 25% = 15 FPS!).
     - Worse: when `shouldSkip == true`, `g_api->vsync()` is NOT called, so 4
       entire frames of 3D GIF draw packets pile up unflushed inside the GS queue
       and then explode onto the PowerVR GE8320 GPU all at once on every 4th
       frame, causing massive 100+ ms stalls!
   Even though `VUThread` on Redmi 10A dropped from `94.8%` down to `64.5%` CPU
   (a 30.3% CPU reduction!), `frameskip=4` was artificially choking presentation
   and batch-stalling `GSThread`!

FIX 1: `ps2x_runtime/src/runner/thread_affinity.cpp`
       Give `GSThread` 100% Exclusive Core 5 (`big_cores[2]`), Move `GIFThread`
       to Core 4 (`big_cores[3]`), and Move `IOPThread` to `little_cores` on
       ALL 8-Core SoCs (Fixes Dimensity 7300 Core 5 Collision!)
--------------------------------------------------------------------------------
In `ps2x_runtime/src/runner/thread_affinity.cpp`, inside `pinCurrentThread()`
(around lines 215–295), replace BOTH the `if (top_tier <= 1 && big_cores.size() >= 4)`
and `else if (big_cores.size() >= 4)` blocks with a single unified `if (big_cores.size() >= 4)`
block so that Dimensity 7300 (`top_tier == 2`) and Helio G25 (`top_tier == 1`)
BOTH isolate `EE_MAIN`, `VU1_WORKER`, `GS_RENDERER`, and `GIF_WORKER` onto the
4 separate Big cores (`big_cores[0..3]`) and isolate `IOP_WORKER` onto
`little_cores`:

```cpp
    if (big_cores.size() >= 4)
    {
        // Unified 4-Big + 4-Little layout for all 8-core SoCs (Helio G25, Dimensity 7300, Snapdragon):
        //   big_cores[0] : EE_MAIN     (dedicated Big core + fallback to big_cores[3])
        //   big_cores[1] : VU1_WORKER  (dedicated Big core + fallback to big_cores[3])
        //   big_cores[2] : GS_RENDERER (100% EXCLUSIVE Big core — never preempted by IOP or GIF!)
        //   big_cores[3] : GIF_WORKER  (dedicated Big core)
        //   little_cores : IOP_WORKER, AUDIO_SPU2, HOST_PUMP (all 4 Little cores)
        switch (role)
        {
        case ThreadRole::EE_MAIN:
            CPU_SET(big_cores[0], &mask);
            if (top_tier <= 1) CPU_SET(big_cores[3], &mask);
            break;
        case ThreadRole::VU1_WORKER:
            CPU_SET(big_cores[1], &mask);
            if (top_tier <= 1) CPU_SET(big_cores[3], &mask);
            break;
        case ThreadRole::GS_RENDERER:
            CPU_SET(big_cores[2], &mask);
            break;
        case ThreadRole::GIF_WORKER:
            CPU_SET(big_cores[3], &mask);
            if (top_tier <= 1)
            {
                for (int c : little_cores)
                    CPU_SET(c, &mask);
            }
            break;
        case ThreadRole::IOP_WORKER:
        case ThreadRole::AUDIO_SPU2:
        case ThreadRole::HOST_PUMP:
            if (!little_cores.empty())
            {
                for (int c : little_cores)
                    CPU_SET(c, &mask);
            }
            else
            {
                CPU_SET(big_cores[3], &mask);
            }
            break;
        }
    }
```

FIX 2: `ps2x_runtime/src/Scheduler/EeScheduler.cpp`

   Why: This fixes the double-VBlank catch-up bug where any frame taking 17.0 ms

   And inside `EeScheduler::skipIdleCycles()` (around line 1020 of `EeScheduler.cpp`),

3. In `EeScheduler::checkpointDue()` (around line 909 of `EeScheduler.cpp`),
   fast-forward `EEThread` idle spin cycles inside `func_0030B148` (`0x0030B148..0x0030B298`)
